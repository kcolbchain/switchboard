01 Protocol Pattern

HTTP 402 Paywall

The simplest agent-payment pattern: gate any HTTP route behind on-chain payment. The caller sends a signed payment envelope; the middleware verifies and passes through. One line of configuration, infinite composability.

Sub-millisecond verification

Signature verification happens in-process with no external calls. A single-thread FastAPI instance handles 4,200+ verified requests/sec.

Five parameters, done

from fastapi import FastAPI
from switchboard.x402_middleware import X402Middleware

app = FastAPI()
app.add_middleware(
    X402Middleware,
    pay_to="0xYourTreasury...",
    asset="0x036CbD53842c5426634e7929541eC2318f3dCF7e",  # USDC on Base Sepolia
    network="base-sepolia",
    price="1000",           # 0.001 USDC per call
    paths=["/agent-only"],
)

@app.get("/agent-only")

02 Protocol Pattern

Escrow & Refund

Trustless escrow for agent-to-agent payments. Caller locks funds with a deadline; provider claims on delivery; either side can dispute within the challenge window. The native-ETH variant is formalized as an EIP.

Escrow Lifecycle
Phase 1
Deposit & Lock
Caller locks funds into the escrow contract with a deadline and challenge period.
Phase 2
Work Performed
Provider delivers the requested service. Both parties can observe progress on-chain.
Phase 3
Claim or Dispute
Provider claims with a signed receipt. If contested, either side files evidence during the challenge window.
Phase 4
Settlement
Funds release to the provider, or refund to the caller if unclaimed past deadline + challenge.
Contract Surface

Four Functions

deposit(provider, deadline, challenge)  // lock funds
claim(escrowId, receipt)                 // provider claims
dispute(escrowId, evidence)              // contest delivery
refund(escrowId)                         // after deadline
Properties

Trustless by Design

Timeoutconfigurable
Challenge periodconfigurable
Mutual cancelsupported
Oracle releasevia OracleAggregator
Native ETHno wrapper needed
EIP statusdraft submitted

03 Protocol Pattern

Streaming Micropayments

Open a payment channel under a budget cap. Stream micro-pays as work is performed. Settle on close. The Stripe-style rail for long-running agent collaborations — without Stripe.

Live Stream Simulation
How It Works

Session-Based Streaming

A session opens between two agents with a negotiated budget cap. Each chunk of work triggers a micro-payment. The session tracks cumulative spend and auto-closes when the cap is reached or either side signals done.

Min payment0.0001 USDC
Max throughput10,000 msg/s
Settlementon close
Overspend protectionbudget cap
Wire Format

ZAP Binary: 10x Smaller

High-volume streams use the ZAP binary wire format. Zero-allocation, zero-GC, ~10x smaller than JSON. The first production consumer of zap_py.

JSON offer~840 bytes
ZAP offer~84 bytes
Compression10.0x
Allocationszero

Verification Path

Notary → ZK Relay

v1 uses notary attestation (low-cost, production-ready). Upgradable in-place to ZK-relay for v2 (Groth16 proofs on LUX). The upgrade is a registry swap, not a protocol change.
