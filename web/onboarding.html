MCP Tools

Tools your agent can call.

The MCP server exposes these tools. Each is gated by your session key and bounded by the spend policy before the wallet co-signs.

wallet tools

wallet_balance

Returns balances per (chain_id, token) from the treasury, with spendable amounts after reserves.

wallet tools

pay

Drives token negotiation, picks the optimal rail (x402/escrow/MPP), and executes within the spend policy.

escrow tools

create_escrow

Locks funds in MultiTokenAgentEscrow — any token, any chain. Timeout + challenge period enforced on-chain.

escrow tools

confirm_payment · request_refund

Confirm delivery or trigger a refund with optional oracle attestation. All on-chain, all auditable.

policy tools

policy_status

Returns live spend vs. cap, daily remaining, policy denials, and session-key expiry in one call.

metrics tools

escrow_metrics

Polls fill rate, average release time, timeout and refund rates — live from contract events.

# Example: list tools via MCP client
import switchboard_mcp

client = switchboard_mcp.connect(
    endpoint="wss://switchboard.kcolbchain.io/mcp",
    session_key="sb_sk_your_key_here",
)

# List available tools (returns schema for each)
tools = await client.list_tools()

# Check your wallet balance
bal = await client.call("wallet_balance")
# -> [{ chain_id: 8453, token: "USDC", balance: "1024.00", ... }]

Operate the wallet
in 3 steps.

Your agent is connected. Here's the exact sequence it uses to pay another agent — from token negotiation through trustless on-chain settlement, without a human in the loop.

Read the full docs
The 3-step payment loop

How the agent pays.

Every agent payment follows this sequence. The wallet handles routing, negotiation, and signing — your agent just calls pay().

1

Token negotiation

The agent calls pay(payee, amount_usd). The wallet's TokenSelector reads your treasury balances per (chain, token) and intersects them with the payee's accepts_tokens[] list. The highest-ranked common token is chosen — no swap needed for the happy path.

# Step 1: agent calls pay — wallet handles the rest
receipt = await client.call("pay", {
    "payee": "0xPayeeAddress…",
    "amount_usd": "10.00",
    # wallet negotiates token + rail automatically
})
# -> { settlement_token: "USDC", rail: "escrow", tx_hash: "0x…" }
TokenSelector protocol v1.2 accepts[] LUX · USDC · ZOO · ETH · DAI
2

Rail selection & signing

The RailSelector picks the cheapest suitable rail based on amount and trustless requirements. FleetBalancer spreads the nonce load across your wallet fleet. The SpendPolicy is enforced before the MPC wallet co-signs — if the transaction would exceed your daily cap or per-tx limit, it's refused with a typed error.

x402 — micropayments escrow — trustless / large MPP — streaming
3

Settlement & receipt

The chosen token is locked in MultiTokenAgentEscrow (or sent via x402 / MPP). The payee confirms delivery; the escrow releases on-chain. A ZAP-wire receipt is anchored on LUX C-chain. The agent receives the tx hash and can poll escrow_metrics for fill-rate telemetry.

# Step 3: confirm delivery (payee side) → escrow releases
result = await client.call("confirm_payment", {
    "request_id": receipt["request_id"],
})
# Escrow releases, LUX receipt anchored, done.

# Query metrics any time
m = await client.call("escrow_metrics")
# -> { fill_rate: 0.94, avg_release_ms: 1840, open_count: 7 }

Security model

The agent never holds the root key.

Session keys are scoped, revocable, and expiring. A compromised agent is bounded by its SpendPolicy. The MPC root key is never on a single machine.

MPC wallet

Threshold signing

Shamir SSS across the signer fleet. No single machine holds the full key — coordinated by MPCWallet.

SpendPolicy

Per-agent caps

per_tx_cap, daily_cap, token_allowlist, expires_at. Every action checked before co-sign.

Fairness engine

Token-bucket fairness

No single agent starves others. Rate fairness and contract-compliance checks layered on top of SpendPolicy.
